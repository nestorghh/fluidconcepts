================================================================================
1. OBJECTIVE
================================================================================

Build a lightweight Python pipeline that periodically collects metadata for
public domain books from trusted external sources. The metadata becomes a
reference corpus for downstream ML:

  - a searchable catalog of known public-domain books
  - semantic search over metadata and preview text
  - duplicate detection against the existing public-domain corpus
  - preventing ML workflows from reprocessing already-public books

Requirements: configurable storage (local + S3), incremental updates, repeated
execution under an external scheduler, minimal dependencies, type hints,
pluggable providers, and a schema that can gain embeddings later without
changing the ingestion pipeline.

3. SOURCE 1: PROJECT GUTENBERG (gutenbergapi.com)
================================================================================

3.1 THE PUBLISHED DOCUMENTATION IS WRONG
----------------------------------------
gutenbergapi.com is a commercial RapidAPI proxy, not an official Project
Gutenberg API. Its published examples give a host and a path that do not exist.

                published                          actually works
  host    project-gutenberg-books-api...     project-gutenberg-free-books-api1...
  path    /api/books                         /books

The two failure modes are distinguishable, which is what made this findable:

  {"message":"API doesn't exists"}          + header x-rapidapi-proxy-response:true
      -> the RapidAPI PROXY rejected the Host header. Wrong host.

  {"message":"Endpoint '/api/books' does not exist"}
      -> the BACKEND rejected the path. Right host, wrong path.

Losing hours to this is easy because the first error looks like an auth problem.

3.2 VERIFIED CAPABILITIES (probe, 2026-08-15)
---------------------------------------------
  lists catalog with no query   yes, GET /books returns everything paginated
  default page size             32
  maximum page_size             100 (larger values silently capped, not rejected)
  stable sort                   yes, sort=ascending orders by Gutenberg ID
  ordering= / order_by=         silently ignored (falls back to popularity)
  total count in response       NO count field; page until next is null
  free tier quota               1000 requests/month
  rate limiting                 aggressive; back-to-back requests 429.
                                12s spacing verified comfortable

sort=ascending matters more than it looks: new books get higher IDs and land at
the END of a stable ordering. That is what makes page-number checkpointing valid.

3.3 THE SUMMARY FIELD (overturned a design assumption)
------------------------------------------------------
The docs imply no summary exists. In reality the list response includes a
`summary` field populated for ~96.5% of records (193 of the first 200 sampled)
with real 600-1200 character editorial abstracts.

This arrives WITH THE LISTING at no extra request cost. It is the spec's
first-choice searchable text, and it demotes the per-book /books/{id}/text
endpoint to a fallback for the remaining ~3.5%.

Without this discovery the pipeline would have spent one request per book on
text - roughly 79,000 requests against a 1000/month quota.

3.4 FIELDS IN THE LIST RESPONSE
-------------------------------
  id, title, alternative_title, authors[{id,name}], subjects[], bookshelves[],
  formats{mime:url}, download_count, issued, summary, reading_ease_score,
  cover_image, removed_from_catalog

`formats` carries real download URLs; the text/plain entry is preferred for
download_url, falling back to a URL derived from the Gutenberg ID (free, no
request needed).

3.5 FIELDS THAT DO NOT EXIST
----------------------------
No language, publisher, media_type, or ISBN anywhere in the response. `issued`
is Gutenberg's own release date, NOT original publication - ID 1 is dated
1971-12-01, and Pride and Prejudice is 1998-06-01 rather than 1813. Confirmed
independently against Project Gutenberg's own RDF metadata.

These stay null in the schema by design, waiting for a richer provider.

3.6 COST MODEL
--------------
  1,000-book PoC                    ~10 requests
  full catalog (~79k) @ page_size=100  ~790 requests
  preview text fallback             1 request per book lacking a summary (~3.5%)

A full backfill fits inside one month of the free tier, but only just.

4. SOURCE 2: HATHITRUST (hathifiles)
================================================================================

4.1 WHAT IT IS
--------------
Bulk TSV dumps, not an API. No key, no signup, no quota.

  index:   https://www.hathitrust.org/files/hathifiles/hathi_file_list.json
  monthly: hathi_full_YYYYMM01.txt.gz   ~1.22 GB, ~19.6M rows
  daily:   hathi_upd_YYYYMMDD.txt.gz    ~6-8 MB,  ~215k rows

NOTE: hathitrust.org's HTML pages return 403 to scripted requests (WAF). The
static file URLs and the JSON index serve fine with a browser User-Agent. Only
the human-facing documentation pages are blocked.

4.2 THE INDEX (hathi_file_list.json)
------------------------------------
A manifest of the downloadable files - contains no book data. Flat JSON array,
currently 73 entries. Six fields per entry:

  filename, full (true=monthly / false=daily), size, created, modified, url

Used for discovery so filenames never have to be guessed. Guessing breaks
because: today's daily may not be published yet (created ~04:38 ET), the
monthly is a job that runs rather than a contract, retention shifts daily, and
you would lose `size` (so you could not warn about a 1.2 GB download).

4.3 FILE FORMAT
---------------
  - gzipped TSV, NO header row
  - 26 columns, fixed order (hardcoded in demo/fetch_books.py as HATHI_COLUMNS)
  - titles contain bare quote characters, so the parser MUST use
    csv.QUOTE_NONE. The default quoting mis-splits rows.

Column order:
  1 htid                  2 access                3 rights
  4 ht_bib_key            5 description           6 source
  7 source_bib_num        8 oclc_num              9 isbn
 10 issn                 11 lccn                 12 title
 13 imprint              14 rights_reason_code   15 rights_timestamp
 16 us_gov_doc_flag      17 rights_date_used     18 pub_place
 19 lang                 20 bib_fmt              21 collection_code
 22 content_provider_code 23 responsible_entity_code
 24 digitization_agent_code 25 access_profile_code 26 author

4.4 RIGHTS CODES - WHICH MEAN PUBLIC DOMAIN
-------------------------------------------
Measured on one daily file (215,373 rows):

  pd       90,710   public domain                      <- PUBLIC DOMAIN
  pdus     13,722   public domain in the US            <- PUBLIC DOMAIN
  pd-pvt      935   public domain, private access      <- PUBLIC DOMAIN
  ic       95,777   in copyright
  und      13,290   undetermined
  icus        292   in copyright in the US
  op           25   out of print
  nobody        2   restricted
  cc-*        ~490  Creative Commons (open, but NOT public domain)

Across the whole August monthly file: 8,129,991 of 19,605,849 rows are public
domain = 41.5%.

The demo filters to {pd, pdus, pd-pvt} by default; --all-rights disables it.

4.5 ARE MONTHLY FILES CUMULATIVE? (tested, yes)
-----------------------------------------------
Each monthly full file is a COMPLETE SNAPSHOT of the corpus, not a diff.

Test: sampled 120,001 htids from the July 1 file, then scanned all 19,605,849
rows of the August 1 file.
  RESULT: 0 missing. Every July id was present in August.
  Sizes: July 1.219 GB -> August 1.221 GB.

Caveat: proven for a 120k sample, not all 19.6M rows. HathiTrust can withdraw
volumes, so zero removals is not guaranteed in general - but nothing in the
sample was removed and the file grew.

4.6 DO THE DAILIES ROLL INTO THE MONTHLY? (tested, yes)
-------------------------------------------------------
Used July's dailies as a natural experiment between the two snapshots.

The July 15 daily contained 9,140 records:
  - 9 NEW records          -> 9 of 9 present in the Aug 1 snapshot   (100%)
  - 495 RIGHTS CHANGES     -> 495 of 495 reflected in Aug 1          (100%)
  - stale (old value)      -> 0

So:   full(Aug 1)  ==  full(Jul 1)  +  all dailies from Jul 2 .. Aug 1

Real transitions observed:
  coo.31924061453225         pdus -> pd     aug1 = pd
  uiuo.ark:/13960/t7np22003   und -> ic     aug1 = ic
  umn.319510007606937          ic -> pd     aug1 = pd

IMPORTANT: rights move in BOTH directions. `ic -> pd` is a book entering the
public domain; `und -> ic` is material leaving it. Treating an old `pd`
determination as permanently true will eventually be wrong.

4.7 DAILIES ARE DELTAS, NOT SNAPSHOTS
-------------------------------------
Aug 17 daily (215,373 rows) against the Aug 1 snapshot:
  - 96.9% already existed  -> MODIFIED records (mostly rights re-adjudication)
  -  3.1% were new         -> genuinely new since Aug 1

So the bulk of daily churn is rights review, not new scans.

4.8 ROW ORDER IS STABLE BUT NOT SORTED
--------------------------------------
Both months open with the same htids in the same sequence, and the order is NOT
htid-sorted. New records are INTERLEAVED into the existing order, not appended.

This caused a false alarm mid-investigation: comparing the first 120k rows of
each month showed 132 "missing" ids. 126 turned up later in the file and the
last 6 turned up on the full scan - all had simply been pushed down by
insertions.

  => Do NOT diff by row position. Do NOT assume the first N rows are a stable
     sample. Join on htid.

4.9 RETENTION IS A ROLLING WINDOW
---------------------------------
Only 2 monthly files and 71 dailies are retained (window observed: 2026-06-09
onward). Older files are deleted, so history cannot be reconstructed from their
archive. Archive locally whatever you need to keep.

4.10 ROWS ARE VOLUMES, NOT WORKS
--------------------------------
A sample of 40 rows contained only 8 distinct titles - the same book scanned by
different member libraries appears once per library. One title appeared 18
times.

For duplicate detection, collapse on oclc_num or title+author. Do not treat each
row as a distinct work.

4.11 PERFORMANCE
----------------
Streaming and parsing the entire 1.22 GB / 19.6M row monthly file took 49
SECONDS. Far cheaper than assumed. The demo streams the gzip and stops early, so
even --full never downloads the whole file when only N rows are needed.

4.12 HATHITRUST FILLS GUTENBERG'S GAPS
--------------------------------------
In a 40-row sample: publication_year, publisher, language and oclc_num were all
populated 40/40 - every field the Gutenberg API lacks entirely. (ISBN was 0/40;
these were pre-ISBN-era volumes.)


================================================================================
5. BUGS FOUND AND FIXED
================================================================================

All four were caught by tests or by live runs, and all four would have shipped
silently.

5.1 Incremental missed newly published books
    Resuming at last_page + 1 skipped the previously PARTIAL final page - which
    is exactly where new books land in an ascending-ID ordering.
    FIX: resume ON the last page, not after it. Costs one request; the content
    hash discards the duplicates.

5.2 Every record looked "changed" on every run
    content_hash included searchable_text, but stage 1 hashes a record BEFORE
    stage 2 fetches its preview text. The stored hash could therefore never
    match a freshly-listed record, causing endless rewrites and wasted quota.
    FIX: exclude searchable_text, text_source, text_char_count from the hash.
    The hash answers one question only: "did upstream metadata change?"
    (download_count and ingested_at were already excluded for the same reason -
    download_count churns constantly.)

5.3 --max-books froze the checkpoint (quadratic request growth)
    The page checkpoint only advances when a page is FULLY consumed. Stopping
    mid-page left last_page behind, so every later run re-read all earlier
    pages. Over a 790-page backfill that is quadratic growth - fatal on a
    1000/month quota.
    FIX: honour the cap to the END of the page it lands on. The cap can now
    overshoot by up to page_size-1 records; that is the deliberate trade.
    Verified live: checkpoint advanced 2 -> 4.

5.4 No request pacing
    The gateway 429s on back-to-back requests. A 790-page backfill would have
    throttled to death. The capability probe only succeeded because requests
    were manually spaced 12s apart.
    FIX: min_request_interval config, default 12s for this source.


================================================================================
6. KEY DESIGN DECISIONS
================================================================================

6.1 Embeddings are NOT stored in the book table
    book_uid ("gutenberg:1342") is a stable primary key. Build a vector index
    separately and join on it. That is what allows adding embeddings, or
    swapping embedding models, without touching ingestion or rewriting the
    corpus. Reserving null vector columns on every row would not.

6.2 Explicit pyarrow schema, never inferred
    A shard where an optional column happens to be entirely null would be typed
    as `null` in that file and as its real type in another, breaking reads
    across the dataset.

6.3 Writes are append-only; latest-wins on read
    A changed record is written again with a newer ingested_at.
    storage/parquet.py:read_catalog() gives the deduplicated view. This keeps
    writers simple and makes runs safely re-runnable.

6.4 Storage backends only move bytes
    Serialization lives in parquet.py, so local and S3 produce byte-identical
    output with identical layout. boto3 is imported lazily - local development
    never needs the AWS SDK.

6.5 The pipeline never imports a concrete provider
    Sources resolve by name from a registry. Adding HathiTrust / Internet
    Archive / Open Library = one new module + a config entry, no pipeline change.

6.6 Quota exhaustion is a clean stop, not a failure
    Exit code 0, state checkpointed, next scheduled run resumes. This is what
    makes the pipeline safe under cron/Actions/Airflow.

6.7 Storage layout (identical local and S3)
    books/provider=gutenberg/ingest_date=2026-08-15/part-0000.parquet
    _state/gutenberg.json
    _manifest/2026-08-15-gutenberg.json
    Hive partitioning means the whole corpus reads in one pyarrow.dataset call.

11. THE OVERLAP EXPERIMENT: IS GUTENBERG A SUBSET OF HATHITRUST?
================================================================================

11.1 WHAT WAS DOWNLOADED
------------------------
  Gutenberg  full catalog  78,875 records, 789 pages, 9,256s (~2.6h), 206 MB JSONL
  HathiTrust monthly full  19,605,849 rows, 1.22 GB gzip, downloaded in 19.5s

The Gutenberg pull cost ~790 of a 1000/month quota, leaving 147. It is resumable
(scripts/download_all_gutenberg.py, superseded by scripts/build_catalog.py):
each page flushes to disk with a checkpoint, so an interruption never re-spends
quota already used.

A rate-limit finding: the 12s pacing in Part I was measured WITHOUT a key. With a
valid key, 1.5s spacing works fine. That cut the run from ~2.6h of pure waiting to
about 30 minutes of real work.

11.2 RESULT - NO, IT IS NOT A SUBSET
------------------------------------
  matching method                  Gutenberg books found   %
  FULL title                       30,451                  38.6%
  MAIN title (subtitles stripped)  41,603                  52.7%
  TITLE + AUTHOR (high confidence) 33,533                  42.5%

Defensible answer: ~42-53%. Roughly half of Gutenberg has no counterpart in
HathiTrust under any title match attempted. Of the confident matches, 31,919
(42.0%) have a HathiTrust copy that is ALSO public domain there.

11.3 WHY THE TITLE-ONLY NUMBER OVERSTATES
-----------------------------------------
Generic titles collide massively: 'poems' matched 4,807 HathiTrust volumes,
'life' 1,891, 'memoirs' 1,440. 1,141 matched titles hit >=50 volumes each,
covering 2,926 Gutenberg books. Requiring author agreement removes most of this,
which is why title+author (42.5%) lands BELOW main-title (52.7%).

11.4 WHY IT ALSO UNDERSTATES
----------------------------
Two different failure modes in the unmatched list:

  genuinely absent (HathiTrust scans print, so these cannot be there):
      The 1990/1991 CIA World Factbook, The 1990 United States Census,
      The Jargon File v2.9.10

  false negatives (present but titled differently):
      "The King James Version of the Bible" / "The Bible, King James Version"
      "The Declaration of Independence of the United States of America"
      "Roget's Thesaurus"

Also, 18.6% of HathiTrust BOOKS have no author at all, so those could never match
under a title+author rule regardless. 42.5% is a LOWER BOUND.

11.5 A NORMALIZATION BUG CAUGHT BEFORE IT MATTERED
--------------------------------------------------
The first MAIN normalization cut titles at ':' or ';' to strip subtitles. But the
two sources use DIFFERENT punctuation for the same convention:

    Gutenberg :  "Moby Dick; Or, The Whale"
    HathiTrust:  "Moby-Dick, or, The whale"

Cutting only the semicolon form made the two sides disagree and turned genuine
matches into misses. Fixed to handle both; validated on five well-known books
(FULL 5/6, MAIN 6/6). The one FULL miss is Twenty Thousand Leagues, where
HathiTrust appends a subtitle Gutenberg lacks - which is exactly what MAIN is for.

12. MATERIAL TYPE: CAN WE FILTER TO "BOOKS"?
================================================================================

YES for format, NO for genre. The bib_fmt column (position 20, 100% populated) is
the MARC record type:

  code  meaning                        rows          %       public domain
  BK    Book                           12,787,978    65.23%  5,278,365
  SE    Serial (journal/annual)         6,581,932    33.57%  2,759,883
  MU    Music / score                     227,226     1.16%     88,786
  MP    Map                                 6,077     0.03%      2,170
  MX    Mixed materials (archival)          1,972     0.01%        384
  VM    Visual material                       575     0.00%        392
  CF    Computer file                          81     0.00%          9
  XX    Unknown                                 8     0.00%          2

Practical books-only filter:

    bib_fmt == "BK" and rights in {pd,pdus,pd-pvt}      -> 5,278,365
    ...and us_gov_doc_flag != "1"                       -> 4,624,169

That second step drops 654,196 government documents. Language is available too:
3.18M English, 576k German, 492k French in the PD book set.

WHAT IS NOT AVAILABLE: there is no genre field anywhere. Poems vs fiction vs
research is NOT derivable from the hathifiles. No subject headings, no LC
classification, no abstracts. (lccn is a CONTROL NUMBER, an identifier - not a
call number, so it classifies nothing.)

Routes to genre, cheapest first:
  1. join to Gutenberg - it has real LCSH subjects and bookshelves, and ~42% of
     Gutenberg overlaps, giving free labels plus a labelled training set
  2. enrich via oclc_num / lccn against WorldCat or LoC
  3. HathiTrust Bib API - full MARC per record, but one request per volume

13.2 FINDINGS
-------------
  * htid is THE unique key - distinct htid == row count exactly, every format.
  * OCLC identifies a WORK/EDITION, not a copy. 9.19M distinct across 19.6M rows.
    The first three rows of the file are three htids sharing OCLC 2779601.
  * OCLC is MULTI-VALUED in ~15.7% of rows ("217097625,252"). Raw vs first-value
    differs by only 149 out of 8.5M distinct book values, so it rarely matters.
  * OCLC is MISSING from 952,005 rows (4.9%), so it cannot be the sole key.
  * The two candidate keys agree within 2% for books (8,531,240 vs 8,352,576) -
    independent derivations landing that close is real mutual validation.

13.3 COLLAPSE RATIO DIFFERS ENORMOUSLY BY FORMAT
------------------------------------------------
  format   all rows   public domain
  Book       1.50x       1.75x
  Serial    13.88x      15.76x
  Music      1.28x       1.22x

Serials collapse ~14-16x because every volume/issue of a journal shares one OCLC.
This is a second strong argument for bib_fmt=="BK": serials are not merely a
different genre, they inflate row counts by an order of magnitude.

HEADLINE: ~3.0 MILLION distinct public-domain books. Not 19.6M rows, not 8.1M
public-domain rows.

  1. rights_date_used uses 9999 as a SENTINEL - 1,477,418 rows (7.54%) mean
     "unknown", not year 9999. Filter before any date arithmetic. NOTE: the demo
     maps this field to publication_year, so ~7.5% of HathiTrust rows display
     9999 unless cleaned (build_catalog.py does clean it).
  2. oclc_num is multi-valued (~15.7%).
  3. oclc_num is not unique per row and missing from 4.9%.
  4. Rows are volumes, not works (see collapse ratios above).
  5. description is NOT a description - it holds volume enumeration (v.5, no.3).
     There is no abstract/summary field anywhere in the file.

15. BOOKS WITHOUT AUTHORS
================================================================================

15.1 RATES
----------
  all rows (every format)        34.6%
  book rows                      18.6%
  DISTINCT books                 16.1%   (1,447,024 of 8,965,717)
  DISTINCT public-domain books   11.9%   (  385,769 of 3,254,537)

Deduplication improves the ratio - authorless books are duplicated slightly less
than authored ones. Public-domain books (older, more often single-author
monographs) are catalogued more completely than the in-copyright mass.

15.2 WHY THE FIELD IS EMPTY
---------------------------
Almost always a work with no single personal author: edited volumes, anthologies,
conference proceedings, corporate/government publications. Example:

    title:   Poems from the Virginia quarterly review, 1925-1967.
    imprint: University Press of Virginia [1969]
    author:  (empty)

The responsible names ARE present - inside the title, after the " / ". MARC
records an author separately only for a personal main entry; editors and
corporate bodies go in the statement of responsibility instead.

By format: SE 66.7% missing, BK 18.6%, VM 46.4%, MP 10.2%, MU 7.0%.

15.3 THE SURPRISE: CATALOGUING IS NEARLY PERFECTLY CONSISTENT
-------------------------------------------------------------
Works where one library recorded an author and another did not: 77. Out of 8.5
million. Essentially zero.

So authorlessness is a property of the WORK, not a cataloguing accident - every
library independently reaches the same conclusion. The practical consequence is
negative: missing authors CANNOT be recovered from sibling copies. They must come
from parsing the statement of responsibility out of the title, or from external
enrichment via oclc_num.

matching rows by scripts/extract_authorless.py.

16. THE COMBINED CATALOG  ->  scripts/build_catalog.py
================================================================================

16.1 DESIGN: THREE INDEPENDENTLY CACHED STAGES
----------------------------------------------
    python scripts/build_catalog.py --download   # both sources; skips if cached
    python scripts/build_catalog.py --build      # merge -> combined.parquet
    python scripts/build_catalog.py --stats      # summarize
    python scripts/build_catalog.py --all
    python scripts/build_catalog.py --build --force   # rebuild only

Nothing re-downloads unless forced. Verified: a second --download --build printed
only "cached ... skipping" for all three stages - zero quota, zero bytes. Each
stage has its own --force so the merge can be rebuilt without re-fetching 1.2 GB.
A manifest.json records what was used to build what.

16.2 THE TABLE
--------------
  19,684,724 rows (19,605,849 hathitrust + 78,875 gutenberg), 18 columns, 1.1 GB

  publication_year, publisher, oclc_num, isbn, lccn, subjects, summary,
  download_count, source_url

16.3 WHY NOT JUST RETURN A DATAFRAME
------------------------------------
19.7M rows is 5-8 GB in pandas. load_combined() instead pushes filters into the
Parquet reader and only materializes matching rows:

    load_combined(source="gutenberg")                     78,875 rows   0.1s
    load_combined(bib_fmt="BK", public_domain=True)    5,357,240 rows   0.4s
    load_combined(columns=["source","rights"])        19,684,724 rows   0.1s
    load_combined(bib_fmt="BK", public_domain=True, language="eng",
                  columns=[...])                       3,175,913 rows   0.4s

Sub-second on every query, including full-table scans, because column selection
means only the needed columns are read. Still returns a real pandas DataFrame.

16.4 TWO ASSERTIONS MADE FOR GUTENBERG (review these)
-----------------------------------------------------
Gutenberg's API has neither field, so to keep columns joinable:
  bib_fmt = "BK"   - mostly true, but its catalog includes the CIA World Factbook,
                     the 1990 US Census and the Jargon File, which are not books
  rights  = "pd", is_public_domain = True
                   - a COLLECTION-LEVEL assertion from PG policy, not a per-record
                     determination like HathiTrust's

Fields Gutenberg genuinely lacks (language, publisher, publication_year, oclc_num,
isbn, lccn) are left NULL rather than guessed, so a null never masquerades as data.

================================================================================
18. RIGHTS FORENSICS - WHAT "IS THIS BOOK PUBLIC DOMAIN?" ACTUALLY MEANS
================================================================================

This section is the most important practical finding of the whole project.

18.1 RIGHTS ATTACH TO AN EDITION, NOT TO A TITLE OR A TEXT
-----------------------------------------------------------
Four HathiTrust copies share the EXACT title string
"Alice's adventures in Wonderland / by Lewis Carroll ; with forty-two
illustrations by John Tenniel." - and they do not agree:

  htid                        rights  access  imprint                      year
  nc01.ark:/13960/t1zc8zk18   pd      allow   Worthington, 1890            1890
  uva.x000877405              pd      allow   D. Appleton, 1866 [c1927]    1927
  inu.39000002601958          ic      deny    R. Clay, [195-]              1959
  mdp.39015032113881          ic      deny    University Microfilms, 1966  1966

Carroll's 1865 text and Tenniel's 1865 illustrations are long out of copyright.
The 1959 and 1966 printings carry their own copyright in typesetting or
reproduction. Same title, same author, same illustrator, different legal status.

=> If you dedup on title+author and then read `rights` off whichever copy
   survived, the answer here is a coin flip.

Safe patterns:
    work_is_pd = all(r in PD for r in copies.rights)      # conservative
    usable     = copies[copies.rights.isin(PD)]           # permissive

For a "is a public-domain copy available?" corpus, the permissive form is usually
right. Here the answer is YES - the 1890 and 1927 copies are pd with access=allow.

18.2 LATEST DETERMINATION FOR THAT TITLE
----------------------------------------
Ordered by rights_timestamp:
  2022-12-31 19:07:31  pd   allow  uva.x000877405       (newest)
  2013-01-31 19:48:10  pd   allow  nc01.ark:...
  2009-04-29 10:30:14  ic   deny   inu.39000002601958
  2006-09-13 17:16:59  ic   deny   mdp.39015032113881

Verified current: all 30 daily update files published since the 2026-08-01
snapshot were scanned, and NONE of the four htids appear in any of them - no
rights re-determination in the last month.

Caution: these are four independent judgments about four different volumes, not
a revision history of one record. The chronology is coincidence, though a telling
one - the two ic copies (1959, 1966 printings) were adjudicated in 2006/2009,
while the two pd copies (1890, 1927) were done in 2013/2022.

18.3 THE ANNOTATED ALICE - WHY A PD TEXT CAN BE ic
---------------------------------------------------
  htid                mdp.39015048847225
  title               The annotated Alice: ... / by Lewis Carroll [pseudonym]
                      Illustrated by John Tenniel. With an introd. and notes by
                      Martin Gardner.
  author              Carroll, Lewis, 1832-1898.     <- NOT Gardner
  imprint             C. N. Potter, [1960]
  rights              ic
  rights_reason_code  ren   (copyright RENEWED - evidenced, not a default)

Martin Gardner wrote every word of the annotations and appears ONLY inside the
title string. Searching the author field for "Gardner" MISSES this book entirely.
Any author-based attribution treats it as a Lewis Carroll book.

Two of its four copies share lccn 60007341 but have DIFFERENT OCLC numbers
(2023589 vs 444355) - the same work catalogued as two editions. A dedup keyed on
OCLC keeps them apart; one keyed on LCCN merges them. No single identifier in
this file cleanly resolves "same book".

18.4 THE 17-COPY ALICE - WHY THE KEY MERGED THEM
------------------------------------------------
17 public-domain rows collapsed into ONE work. They are 17 genuinely different
editions: 17 distinct OCLC numbers, 17 distinct imprints, 17 distinct
ht_bib_keys, spanning 1869-1929 across 7 libraries.

They merged because every raw title differs ONLY after the " / ":

    ... / by Lewis Carroll ; with forty-two illustrations by John Tenniel.
    ... / by Lewis Carroll ; illustrated by Arthur Rackham ; with a proem ...
    ... / Lewis Carroll ; edited by Clifton Johnson ; illustrations by Tenniel.

norm_full() cuts everything after " / ", so all 17 reduce to the same string. The
key contains no imprint, year, publisher or OCLC - the only fields that
distinguish these editions are exactly the ones it discards.

Right or wrong depends on the question:
  as DISTINCT WORKS   - correct. 17 printings of one 1865 book.
  as DISTINCT EDITIONS- wrong. It merged an 1869 printing with a 1928 one, and
                        merged pd with pdus records.

Note it does the OPPOSITE elsewhere: "Alice in Wonderland" and "Alice's
adventures in Wonderland" stay SEPARATE despite being the same text. The key
over-collapses on the suffix and under-collapses on the prefix simultaneously -
inherent to exact-matching a normalized string.

18.5 A COMMERCIAL REPRINT (the Amazon case)
-------------------------------------------
  ASIN B0DNJ7VYLB, ISBN 979-8300355159, "Independently published",
  2024-11-18, 110 pages

  * NOT in HathiTrust (0 matches). The 979-8 block is Amazon KDP's; HathiTrust
    scans library holdings, and only 544 of 18.1M dated rows are 2024 or later.
  * The WORK is public domain - Gutenberg #11 (82,955 downloads) has the full
    text free, and Gutenberg #114 has the Tenniel illustrations separately.
  * Selling a public-domain work is legal. Whatever the edition ADDS (new
    commentary, introduction, cover, typesetting) is new authorship with its own
    copyright.

As a pipeline test case this is instructive:
    identifier lookup  -> NO MATCH (a 2024 KDP ISBN will never be in an archive)
    title + author     -> STRONG MATCH (Gutenberg #11, HathiTrust pd copies)
    correct answer     -> base text public domain, added apparatus is not

A system that stops at the identifier returns "unknown"; one that stops at the
title returns a confident but incomplete "yes". Encode that asymmetry
deliberately rather than treating a failed ISBN lookup as "unknown".


================================================================================
19. RIGHTS TIMELINES  ->  third dashboard tab
================================================================================

19.1 WHAT THE DATA CAN AND CANNOT SHOW
--------------------------------------
A hathifile row stores ONE rights value and ONE rights_timestamp - the CURRENT
determination for that volume. There is NO history column. A true per-volume
change log is only reconstructible by diffing successive daily files (Part I
section 4.6 measured 495 genuine rights changes in a single July daily).

What the tab shows instead: the sequence of determinations HathiTrust made across
the different COPIES of one work (title + author), ordered by decision date. The
tab states this limitation explicitly so the chart is not misread.

19.2 SCALE  (scripts/rights_timelines.py, books only)
-----------------------------------------------------
  works with >=2 distinct rights values   124,430  (1.48% of 8,402,380)
  ...ever flipping INTO public domain       54,837
  ...with 3+ distinct rights values         11,123
  most transitions on a single work            296

Outputs: demo/output/rights_timelines_summary.{parquet,csv} (124,430 works),
rights_timelines_events.parquet (865,963 events), rights_timelines.json (top 400
for the dashboard).

Ranking note: a raw transition count is dominated by 1,200-copy multi-volume sets
that render as noise, so display ranking prefers works with several distinct
rights values, a real time span, and 3-40 copies - stories a reader can follow.

19.3 EXAMPLE
------------
Andersen's Fairy Tales (ed. Svend Larsen), 25 copies, 5 distinct rights, 18 years:

  ic -> und -> pd -> ic -> und -> pdus -> pd -> ic -> pd -> icus -> ic -> pd ->
  ic -> pdus -> pd

  1887 Belford Clarke / 1922 Saalfield printings   -> pd
  1967 University Microfilms reproduction          -> ic
  1932 Harrap edition                              -> icus, reason gatt
                                                      (GATT/URAA restoration:
                                                       a foreign work's US
                                                       copyright restored by treaty)

19.4 THE TAB
------------
Inline SVG per work: a time axis with a colour-coded dot per determination, and a
connecting line drawn only where consecutive outcomes DIFFER, so changes read as
visible steps. Hover gives rights - date (reason). Colours group by meaning:
green = public domain, red/orange = restricted, grey = undetermined, blue = cc-*.
Filters: title/author search, "only works that reach public domain", and a
minimum-distinct-rights selector. Clicking a work shows every determination with
date, rights, reason, access, year, imprint and htid.


================================================================================
20. CASE STUDY: THE TEBTUNIS PAPYRI - WHY "24 COPIES" IS MISLEADING
================================================================================

20.1 WHAT VARIES ACROSS THE 24
------------------------------
12 of 26 columns vary; 14 are identical.

  VARIES:    htid (24), description (18), rights_timestamp (15),
             source_bib_num (11), collection_code (11), source (10),
             content_provider_code (10), responsible_entity_code (10),
             rights (5), rights_reason_code (5), access (2),
             digitization_agent_code (2), access_profile_code (2)

  IDENTICAL: title, author, imprint, oclc_num, lccn, ht_bib_key (000908205),
             rights_date_used, lang, pub_place, bib_fmt, isbn, issn,
             us_gov_doc_flag

One ht_bib_key, one OCLC, imprint "H. Frowde, Oxford University Press [etc.]
1902-" (the trailing dash marks an open-ended set). These are NOT 24 copies of one
book - they are roughly 5 distinct VOLUMES held by 10 libraries. The description
column carries the volume enumeration: I, II, III:pt.1, III:pt.2, v.1, v.2, v.4,
v.1 pt.1, P.Tebt. I, V.3 PT.1, 4:2, v.25 ...

Rights differ BY VOLUME because the volumes were published years apart:
  v.1, v.2 (1902-07)  pd / pdus   (gfv, add)
  III pt.1            ic          (add)
  III pt.2            icus        (gatt - US copyright restored by treaty)
  v.4                 MIXED       (see below)

20.2 THE v.4 DISAGREEMENT
-------------------------
Six copies all labelled "v.4" do not agree:

  htid                        rights  reason  library      decided
  iau.31858002243172          pd      add     Iowa         2024-05-17
  uc1.31822028307387          pd      add     California   2024-05-17
  uiuo.ark:/13960/t5z67wx2d   pd      add     Illinois     2024-05-16
  mdp.39015070410306          pd      add     Michigan     2024-05-17
  coo.31924011864240          ic      bib     Cornell      2026-05-10
  umn.319510011939465         und     nfi     Minnesota    2015-02-18

Confirmed independently via the public HathiTrust Bib API
(catalog.hathitrust.org/api/volumes/full/json/recordnumber:000908205), which
returns the same 24 items with the same rights codes.

20.3 THE MARC RECORD EXPLAINS IT
--------------------------------
Two notes from the bibliographic record:

  "The first four volumes are numbered: part I, part II, vol. III, part I,
   vol. III, part II."

  "vol. IV has imprint: London published for the British Academy by Egypt
   Exploration S[ociety]"

So "v.4" is AMBIGUOUS. Under that enumeration the FOURTH PHYSICAL VOLUME is
vol. III part II - but there is also a genuine Volume IV from a different
publisher, decades later. Six libraries writing "v.4" in a local holdings field
were probably not all describing the same book.

Read that way the rights are not contradictory: an early Oxford volume being pd
and a later EES volume being ic are both plausible, and Minnesota's und/nfi is an
explicit "no further information". STRONG HYPOTHESIS, NOT PROOF - confirming it
needs the scans or per-item publication dates, neither of which the hathifiles
nor the Bib API expose.

20.4 CAN THE CONTENT BE COMPARED? NO
------------------------------------
  * hathifiles contain no content, only metadata
  * babel.hathitrust.org returns HTTP 403 (Cloudflare) to automated requests
  * two of the six are access=deny and not viewable by anyone without permission

20.5 CONSEQUENCE FOR THE PIPELINE
---------------------------------
description CANNOT be trusted as a volume key. It is free-text local holdings
data, 50.2% populated, with no standard format - this one set shows I, v. 1,
v.1 pt.1, P.Tebt. I, 4:2 and V.3 PT.1 for the same series.

An earlier suggestion of (ht_bib_key + description) as a key would merge these six
and pick one rights value, silently blending an in-copyright later volume with
public-domain early ones. For a public-domain corpus the safe rule is PER-htid:
treat each scan's own rights as authoritative for that scan, and do not propagate
a pd verdict across copies sharing a description string.
